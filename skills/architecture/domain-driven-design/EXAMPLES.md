# Domain-Driven Design Examples

## Implementation example
Request: Use the Domain-Driven Design skill to add a small feature in the current repository, follow existing conventions, and verify with model walkthroughs, invariant tests, boundary reviews, repository contract checks, and language consistency checks.

Expected output: A focused implementation summary, changed files, verification results, and notes about Domain-Driven Design-specific risks.

## Review example
Request: Use the Domain-Driven Design skill to review a pull request for correctness and risks.

Expected output: Severity-ranked findings that call out issues such as anemic models, leaking persistence concerns, oversized aggregates, unclear boundaries, and jargon without domain meaning.

## Debugging example
Request: Use the Domain-Driven Design skill to investigate a failure involving bounded contexts, aggregates, value objects, domain services, ubiquitous language, and context mapping.

Expected output: Root cause, focused fix or recommendation, verification evidence, and remaining uncertainty.
